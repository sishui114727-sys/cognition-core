# 检索设计：BM25 / 向量 / 时序 / 拒识

更新时间：2026-10-29
结论先行：**混合检索的架构可以接，而且今天就能做；向量通道本身卡在"没有 embedding 来源"，不是卡在算法。**

---

## 一、这个插件能干什么、不能干什么

先说硬约束（已查证，不是推测）：

```text
宿主 config.json 里没有任何 embedding 配置
宿主 src/*.js 里没有 embedding / vector 相关调用
插件以目录形式分发，不带 node_modules；package.json 无 dependencies
  → sqlite-vec、onnxruntime 这类原生/第三方依赖进不来
Node 24 自带 node:sqlite，但它不能加载原生扩展
  → 想在 SQLite 里做向量检索这条路是堵的
```

所以向量只有一条可行路径：**纯 JS 余弦 + Float32Array 侧车文件**，懒加载、增量更新。
代价是 O(N×D) 全扫，必须先用词法/时间把候选压到几千条再算。

代码已经留好接口（`src/retrieval.js`）：

```js
retrieve({ events, cognitions, query, scope, now,
           embedder: { embed(texts) -> Float32Array[], vectors: Map<'type:id', Float32Array> } })
```

`embedder` 不传 → 只走词法，**绝不假装有语义能力**；向量抛错 → 自动退回词法并在 `vectorUsed=false` 标注。

## 二、你列的五个问题，对这套系统的实际影响

| 你的判断 | 在本场景的结论 |
|---|---|
| ① 向量对精确信息差 | 成立。我们本来就用 BM25 + 中文二元组：`3431047779`、`BV1xx...`、`牢猫` 都能精确命中；向量只做补充，RRF 保证它压不死关键词 |
| ② 长文本分块是工程债 | **本场景基本不成立**：记忆原文是单条 ≤240 字的对话 turn，不存在长文切块。只有接入 B 站字幕/长文档时才需要，那时要单独设计，别套在对话记忆上 |
| ③ 时序盲区 / 矛盾坍缩 | 已经动手：`recency` 半衰期重排、`status` 权重（stable 1.15 / contested 0.6 / retired 硬过滤）、`sinceDays` 硬时间窗。仍缺 `superseded_by` 显式指针 |
| ④ 语义熵坍缩 | 影响小（短文本 + 中文），但它正好是"别把向量当主通道"的理由 |
| ⑤ 自研嵌入门槛高 | 不做。要用就用现成 API 或本地小模型，精力花在检索纪律上 |

## 三、实测：词法检索够快，但拒识做不到

语料：真实 `events.jsonl` 3852 条（21 条 dialogue + 迁移历史）。

```text
查询延迟     8–17ms（单次全量 BM25，3852 文档）
10 次平均    10.5ms
```

拒识实验（相关 vs 无关，各 4–7 条）：

```text
相关   鸟鸟            coverage 1.00   maxIdf 7.34
相关   3431047779      coverage 1.00   maxIdf 6.12
相关   可绫是谁         coverage 0.73   maxIdf 7.85
相关   鸟鸟的QQ是多少    coverage 0.33   maxIdf 7.34   ← 正常追问，覆盖却很低
无关   今天晚饭吃什么    coverage 0.36   maxIdf 6.55   ← 和上面几乎一样
无关   那个记错了的人是哪个 coverage 0.19 maxIdf 5.24
```

**结论：词法统计分不开"相关的专有名词"和"稀有的无关二元组"。**
所以 `minCoverage` 默认 0（关闭），只保留最可靠的一条：**零命中必拒**。
硬拒识需要语义通道或模型判定；在没接向量之前，硬拒会误伤正常追问——这条写进了代码注释。

另一个可选路径是不硬拒，而是注入"未找到可靠记忆（置信 x）"给模型，让它知道可以说不确定。
这比静默塞噪声好，也比静默清空好。

## 四之二、注入路径踩过的三个坑（0.22.8–0.22.10，都有实测）

1. **`core.recall` 是子串匹配**：`row.text.includes(query)`。自然提问几乎永不命中，
   而 `cognition_recall` 工具走的是 retrieve —— 于是"工具里能用、注入里永远静默"。
2. **检索词用错**：拿整条 user 消息当 query（7495 字符 / 2331 token），coverage 稀释成 0.00，
   门槛直接拒召。改成「本轮对方最后一句原话」后同一句话 10–24 token、coverage 1.00。
3. **自检索偏差的假数据**：早期我拿"库里已有事件的原文"当查询词去检索它自己，
   得到 coverage 0.72–1.00，看着很漂亮，**这个测量是无效的**。
   真实新句子的实测：`大肥鱼，之前我说让claude帮我做歌曲mv…` coverage 1.00（合格）；
   `你给我封的什么号` 0.40；`牢大到底是谁啊` 0.31；而无关的 `今天晚饭吃什么` 0.27。
   —— 后两组几乎不可区分，再次印证"词法统计做不了拒识"。

注入门槛因此定在 `minCoverage=0.5`：宁可这一轮不注入，也不塞噪声。
拿不到本轮原话时直接跳过（不退回整条 user 消息），并在 KNOWN_ISSUES KI-007 记录取舍。

## 五、如果要接向量，先回答这三个问题

1. **embedding 从哪来？** 本地小模型（要额外运行时）还是 API（要网络 + key + 成本 + 隐私）？
   没有这一条，向量通道就是空转。
2. **规模多大再值得？** 现在 21 条 dialogue、未来每天几十条，BM25 已经够。
   经验阈值：**同一 scope 超过 5000 条事件**时，语义补充才开始划算。
3. **拒识靠什么判定？** 若要用向量做拒识，需要一个校准过的相似度阈值；
   实测余弦在短中文对话上分布很挤（你说的熵坍缩），大概率还是得靠"低置信标记 + 模型自述"。

## 六、建议的落地顺序

```text
P1（已完成）  BM25 + 时序 + 状态权重 + RRF 骨架 + 零命中拒识
P2            superseded_by；把 retrieve 接进 cognition_recall（只读工具先验证）
P3            确定 embedding 来源后，加向量通道；先离线评测 Recall@5，
              确认"专有名词不被向量挤掉"再上线
P4            规模过 5k 条再考虑 ANN；之前全量扫描足够
```

一句话：**先把检索纪律做对，向量是最后一块拼图，不是第一块。**

## 七、0.23.19 的评测基线（2026-10-31）

`scripts/eval-retrieval.mjs` 是只读评测工具，从真实语料里自动造查询。今天第一次量：

```text
专有名词/低频词查询 100 条：hit@1 82%  hit@3 100%  hit@8 100%  MRR 0.910
同义改写查询 36 条（改写后与原文零共享双字块）：hit@1 0%  ← 语义缺口的上限
现实负例 10 条（用日常词问不存在的事）：拒识 4 条，误纳 6 条
```

**第一项不能当召回率用。** 它属于本文第三节写过的"自检索偏差"：
查询词正是从目标原文里取的罕见词，词法必然赢。它只能证明一件事——
**专有名词/编号类查询不需要向量**，而这恰好是纯向量最容易翻车的地方。

**第三项才是真问题。** 10 条日常负例有 6 条被硬塞结果（`minCoverage=0` 时只有零命中才拒）。
这和第三节的结论一致：词法统计分不开"稀有的无关双字组"和"真正相关的专有名词"。

**第二项是设计性上限**：改写后零共享词，任何词法都是 0。但要注意，
300 词的同义词表就能把这类查询拉回一部分（1 小时、零依赖、可审计），
向量补的是同义词表覆盖不到的长尾。

### 因此路线调整为

```text
P3a  真实问题集（防自检索）：用主人真实问过的问题 + 当时命中的事件，
     以及改写后仍有部分词重叠的"半改写"查询。工具里加 --cases 支持外部用例文件。
P3b  向量通道：Ollama + bge-m3（本地 127.0.0.1，数据不出机器），
     离线脚本建 Float32Array 侧车，模型名/维度/文本哈希随向量一起存，便于失效重建。
     实测纯 JS 余弦 5000×768 全扫 5.7ms —— ANN 与 sqlite-vec 在这个规模没有必要。
P3c  拒识校准：词法覆盖 + 向量相似度双信号（两者都低才拒），
     用现实负例集当验收标准：拒识率上去、且正例不被误拒，才算接对。
```

一句话：**先修拒识，再接向量；评测集不防自检索，数字就是自欺。**

## 八、向量通道实测结论（2026-10-31，Ollama + bge-m3）

装好了 Ollama 0.40.13 + bge-m3（1024 维），全量 4873 条事件离线建向量 67.8s / 19MB，
纯 JS 余弦全扫 5.7ms（5000×768）。单条查询嵌入：模型已加载时 21–25ms，冷启动 5.4s。

评测（同一个语料，只换检索配置）：

| 配置 | 事件查询 hit@1 | 同义改写 hit@1 | 现实负例拒识 |
|---|---|---|---|
| 纯词法 | 82–83% | 0% | 4/10 |
| 向量只在词法零命中时启用（gate=1） | 83% | 11% | 0/10 |
| 向量与词法并列 RRF（gate=2） | 68% | 11% | 0/10 |

**结论：向量通道现在不是净收益。**

1. **原始余弦在短中文上不可用**：无关句也能到 0.94–0.98。去均值（中心化）后
   无关对均值从 0.435 掉到 −0.065、相关对 0.659 → 0.322，间隔 0.22 → 0.39，才有区分度。
   所有向量检索都必须先减语料均值，这一步已经做进 `src/vectors.js`。
2. **增益很小**：同义改写从 0% 到 11%（纯向量排序能到 22%，与词法融合反而被稀释）。
3. **代价是拒识退化**：向量通道对任何查询都能给出候选，`top.length===0` 这个拒识条件
   永远不成立，现实负例从 4/10 掉到 0/10。**接向量等于把"没有相关记忆就明说"的能力关掉。**
4. **不能拿向量分做拒识**：正例目标分最低 0.114，负例最高分 0.484——完全重叠。
   这正是第三节预判的"余弦在短中文对话上分布很挤"。

因此这一版**只交付离线能力，不接进运行时**：

- `scripts/build-vectors.mjs`：建向量侧车（幂等，模型/维度/文本哈希随行存）
- `src/vectors.js`：读侧车 + 中心化余弦
- `src/embedder.js`：Ollama 客户端（keep_alive、800ms 超时、失败抛错不返回零向量）
- `src/retrieval.js`：`semantic` 通道（外部算好查询向量传入，retrieve 保持同步）
- 配置开关**先不加**：加了就是让用户能打开一个会让拒识退化的功能。

### 下一步的顺序（不变，但更具体）

``````text
P3c-1  先修拒识：现在的 minCoverage 门槛因为误拒正常追问被关掉了（第三节），
       需要一份"该拒/该召"的标注集来定阈值，而不是拍一个数。
P3c-2  再决定向量位置：如果只用于 cognition_recall 这类显式调用，
       返回几个额外候选是可接受的；注入路径继续纯词法。
P3c-3  同义词表（300 词，人工审）能吃掉同义改写里很大一块，成本一小时且可审计，
       应当在向量之前先做——它能被解释，向量不能。
``````

## 九、同义词表：先做便宜、能解释的那一半（0.23.20）

51 组近义词（154 个词），`src/synonyms.js`。查扩展在 `scoreLexical` 里做：
查询词命中不到时，看文档里有没有它的等价词；同义词命中的频次与覆盖率都打六折
（`synonymWeight=0.6`），避免「打车」把「攻击」顶到前面。

评测（同一语料，只换配置）：

| 指标 | 不展开 | 展开 |
|---|---|---|
| 同义词覆盖查询 hit@1 | 0% | **23%** |
| 同上 hit@3 | 0% | **38%** |
| 同上 hit@8 | 0% | **53%** |
| 专有名词查询 hit@1 | 79% | 79%（无回退） |
| 现实负例拒识 | 4/10 | 4/10（无回退） |

**怎么读这组数**：

- 构造方式是"事件里出现词 X → 查询换成 X 的同义词"，所以它测的是**这张表覆盖到的那部分
  能不能召回**，不是泛化能力。表外的同义词对仍然是 0。
- hit@1 只有 23%，但 hit@8 有 53%：匹配大多成功了，问题是**排序**——
  查询是几个同义词的词袋（如「图片 照片」），在几千条群聊里会同时命中大量事件。
  真实用户的提问是一整句，歧义比这低。
- 没有回退是关键：扩展只增加命中、不改变命中词的原有权重，所以专有名词查询和拒识都没变差。

**边界**：歧义单字（打、搞、弄）一律不入表。测试 `ambiguous single characters stay out of the
synonym table` 盯着这条，防止以后有人图省事把「打」加进去。

**没做**：注入路径（`context-pack.js`）用的是单字重合判定，不是 BM25；要让它吃同义词，
需要把 relevance 从字符级改成词级，属于另一件事，暂不动。

## 十、拒识标注集与阈值（0.23.21，P3c-1）

`scripts/eval-refusal.mjs` 带一份 22 条标注（recall 7 / refuse 15），每条附判定理由。
**标注是我做的，不是主人做的**：判据是"同一 scope 的语料里到底有没有能回答它的证据"，
不是"检索排第一就算对"（那是自检索偏差）。样本小，只用于筛规则方向。

每条用例回到它原本的 scope 里评测——群聊原句不拿到私聊语料里比覆盖率。

| 规则 | 误拒 / 该召 | 误纳 / 该拒 |
|---|---|---|
| R0 只有零命中才拒（0.23.20 前） | 0/7 | 15/15 |
| 覆盖率 < 0.20 才拒 | 2/7 | 3/15 |
| 覆盖率 < 0.30 才拒 | 5/7 | 1/15 |
| **覆盖率 < 0.25 且 maxIdf < 5 才拒（采用）** | **0/7** | **6/15** |
| 覆盖率 < 0.25 且 maxIdf < 6 才拒 | 1/7 | 4/15 |

采用第三行的理由：**不损失任何该召的查询**，同时把误纳从 15 条降到 6 条。

为什么需要 maxIdf 兜底：长查询的覆盖率会被"到底/是谁/怎么样"这类高频词稀释，
「鱼，你晚上会休息吗？」覆盖率只有 0.11，但它确实命中了一条相关往返（maxIdf 5.71）。
只看覆盖率会把它误拒。

**诚实边界**：剩下 9 条误纳是"稀有词巧合"——「帮我看看明天的机票价格」命中了语料里某个
稀有的二元组（maxIdf 6.15），于是没被拒。这正是第三节说的"词法统计分不开稀有的无关二元组和
真正相关的专有名词"。要再往下走只能靠语义判定或模型介入，不是调阈值能解决的。

阈值写在 `cognition_recall` 的调用处（`minCoverage: 0.25, maxIdfFloor: 5`），
retrieval 的默认值仍是 0（库层不替调用方做业务决定），测试锁住兜底行为。
